# EmoBlocks 开发与验证计划

更新：2026-09-14。关联：[产品方案与创新性分析](EmoBlocks-idea-overview.md)。

## 1. 开发目标与范围

围绕一个核心任务开发：创作者修改音乐块的情绪或长度后，系统保留指定旋律和已确认内容，只修改必要的音乐块并修复前后连接。

已有歌曲片段、原创 MIDI 和分轨是同一套积木的素材来源；串烧、影视、游戏、社交配乐是应用场景。第一版采用线性时间线和离线渲染。后续复用相同积木与连接计划实现互动播放。

**状态说明**：当前为方案，未完成模型部署、音频实测或 DAW 集成。下文能力来源于官方说明；可复用性、效果、硬件和依赖仍需小样本验证。所有工期、阈值均为计划值。

### 核心演示

输入一段原创八小节 MIDI 及伴奏素材，建立“平静→怀疑→冲突→释怀”四个积木，形成 60–90 秒作品。锁定主旋律音高和首尾积木，修改冲突段的节奏密度及长度，系统展示影响范围、重编目标段、修复两侧连接并导出可编辑结果。

时长测试分两种：固定节拍模式使用整小节长度；镜头同步模式要求增加十二秒等精确时间时，系统需调整许可范围内的乐句或过门。若与固定 BPM、整小节、锁定结束时间相冲突，应报告不可同时满足，不能暗中破坏约束。

## 2. 需要自主实现的核心

| 模块 | 自主贡献 | 验收要点 |
|---|---|---|
| 积木约束表示 | 统一描述主题、素材、修改权限、时长与连接条件 | MIDI 锁定和音频锁定有不同的明确语义 |
| 影响范围计算 | 从一次修改推导受影响的块、连接、时间位置和效果尾音 | 未受影响素材缓存可复用；影响范围可解释 |
| 约束编排器 | 综合时间、情绪、主题、节拍和渲染成本选择方案 | 硬约束优先；不可行时返回冲突 |
| 连接修复器 | 对新片段与两侧上下文联合选择边界及过门 | 达到安全条件且通过试听；保留原方案可撤销 |
| 验证与交付 | 检查锁定、修改范围与音乐质量，交付可编辑工程素材 | 每次输出关联项目版本、来源和参数 |

基础分析、音频效果和生成模型采用可替换适配器。接入模型本身不计为算法创新。候选贡献是上述模块在真实修改任务中的联合收益。

## 3. 阶段排期与验收

估算前提：3～4 人、至少一人熟悉 MIDI/配器或 DAW、现成素材和模型可用。4～6 周用于受控验证型 MVP；各阶段可由团队交叉开展，以下周期不是简单相加。未指定比赛期限，暂不绑定日历日期。

| 阶段 | 预计工作窗口 | 主要工作 | 完成门槛 |
|---|---|---|---|
| P0：素材与基线 | 第 1 周，2–3 天 | 准备原创旋律、分轨、人工版本和修改任务；确定机器与单个 DAW | 三组素材可播放；约束与对照任务可复现 |
| P1：积木数据与渲染 | 第 1 周，3–5 天 | MIDI/WAV 导入、统一时基、版本、缓存、基础拼接和导出 | 同一输入可重复渲染；多轨起点和长度对齐 |
| P2：编辑器与约束 | 第 2 周，4–6 天 | 积木、连线、曲线、锁定、影响范围预览、撤销 | 修改指令能变成结构化变更；锁定不被越过 |
| P3：局部重编和连接修复 | 第 2–3 周，5–8 天 | 规则变奏、时长规划、相邻边界修复、效果尾音处理 | 四块演示可完成局部修改并保留其他内容 |
| P4：模型候选接入 | 第 3–4 周，3–6 天 | 复现一个伴奏或可控生成项目，比较候选与规则结果 | 模型失败时可回退；结果经过同一约束检查 |
| P5：对照实验与 DAW 交付 | 第 4–5 周，4–6 天 | 盲听、修改任务、分轨与 MIDI 导入 DAW、错误修复 | 输出实验记录；在一个 DAW 内验证可编辑交付 |
| P6：歌曲素材与长作品 | 第 5–6 周，4–7 天 | 引入自动结构拆分、人工纠正、混合素材、7–8 分钟作品 | 长作品无累计时间漂移；局部编辑仍可控 |

48～72 小时比赛可压缩为：预标素材→四块编辑→一次局部修改→边界修复→前后对比。需明确哪些音频为预生成，不将缓存试听描述为实时模型推理。完整生成、插件、无限分支和多平台集成不纳入短时版本。

## 4. 各环节实现设计

### 4.1 素材、时基与积木

建议结构：

```text
MusicBlock
  id / version / source_asset / source_hash
  representation: midi | audio | stems
  theme_id / role / feature_confidence
  beat_grid / key / meter / duration_bounds
  locks: pitch | rhythm | velocity | region | arrangement
  allowed_edits / target_emotion / variants
  entry_points / exit_points / rendered_asset

Connection
  source_id / target_id / transition_type
  allowed_boundary_window / overlap / tail
  harmonic_rules / tempo_rules / repair_budget

Project
  blocks / connections / emotion_curve
  duration_policy / fixed_anchors / revision
```

MIDI 使用 ticks/拍作为音乐时基，渲染使用采样帧，镜头使用秒/时间码，统一通过 Tempo Map 转换。分清源文件时间、块内时间和项目时间。换速度之后重新计算映射。

MIDI 锁定可精确比对事件；音频锁定直接复用文件或采样区间。由混合音频推测旋律再重新生成不能保证原样保留，界面需显示为“参考主题”而非“精确锁定”。

### 4.2 情绪曲线转成可执行目标

首先暴露能量、张力和疏密三个维度，保留自定义标签；情绪正负倾向作为可选表达。不要将“张力”“能量”和“唤醒度”当作同义词。

将目标曲线采样到乐句/小节，得到候选配器、音符密度、力度、和声张力和音域目标。先使用透明规则和制作者校准，再引入情绪估计模型。相同规则对不同曲风未必成立；音量变化不能作为情绪改变的唯一证据。

LLM 仅把“第二段更紧促，但旋律不变”解析为可校验编辑指令；播放、渲染和硬约束由确定性程序处理。无 API 时提供表单完成全部核心任务。

### 4.3 初稿编排

第一版采用“少量候选＋规则打分＋有限搜索”，先选主题一致、节拍明确的素材。优化项包括情绪偏差、和声/节奏边界成本、主题变化程度和修改量。

硬约束：锁定事件、绝对时间锚点、允许的变速范围。软目标：情绪曲线接近程度、配器喜好、适度复现主题。候选增多后再评估 OR-Tools；没有必要一开始采用复杂优化器。

### 4.4 局部修改与连接修复

1. 保存当前项目版本，解析修改及锁定条件。
2. 计算依赖：目标块、入边、出边、效果尾音、必要的后续时间映射。
3. 检查是否可行；固定总长时只能从允许变化的块分配长度。
4. 生成或选择候选，锁定旋律采用保留原 MIDI 轨/音频层的方式。
5. 使用两侧上下文规划退出点、进入点、过门和配器交接。
6. 重渲染必要的区域；缓存键包含素材、参数、上下文、模型版本与随机种子。
7. 检查硬约束并比较边界质量，输出差异及试听，接受后写入新版本。

最低策略支持整小节配器交接、渐变、短过门。宽泛跨调、强行变速或复杂人声重叠暂时提示替换候选。为混响/Delay 保留足够上下文；不能只裁一段音频就认为所有后续输出完全独立。

锁定“块内容”与锁定“最终混音采样”需区别：整体响度归一化和主总线效果会改变所有采样。MVP 固定总线参数，先验证未修改分轨区间，再报告最终混音中实际受到影响的区域。

### 4.5 渲染与交付

离线渲染优先。建议 WAV 作为内部无损素材，最终编码时统一处理。所有 Stem 从共同项目零点导出，附 MIDI、Tempo Map、块位置及连接清单。

MIDI 不保存软件乐器音色，Tempo/Marker 导入表现也会因 DAW 而异。第一轮选 REAPER 做端到端验收，再扩展 Ableton Live/Logic 等；未测试的软件仅标注计划支持。

音乐生成模型直接输出的是音频时，不承诺自动获得精确 MIDI 或独立可编辑乐器轨。MVP 的 MIDI 与音频由符号编排路径共同产生；模型音频可作为额外层或候选。

## 5. 可复用或借鉴的项目

“工程组件”表示拟作为依赖使用；“研究参考”表示先小规模复现，不能按即插即用库估算。论文代码、权重和数据许可证分别确认后再纳入交付。

| 项目 / 官方来源 | 类型与使用阶段 | 具体用途 | 边界与验证任务 |
|---|---|---|---|
| [pretty_midi](https://github.com/craffel/pretty-midi)、[mido](https://github.com/mido/mido) | 工程组件，P1 | MIDI 解析与输出 | 实测 Tempo、力度、控制器及多轨往返 |
| [librosa](https://github.com/librosa/librosa) | 工程组件，P1/P6 | 节拍、Chroma、Onset、能量 | 检查半速/倍速错误；不将能量当作情绪真值 |
| [All-In-One](https://github.com/mir-aidj/all-in-one) | 研究推理组件，P6 | 节拍、强拍与功能段落分析 | 先测目标曲风；保留人工边界纠正；依赖隔离 |
| [Demucs](https://github.com/facebookresearch/demucs) | 分离候选，P6 | 混合歌曲提取人声、鼓、低音等 | 分轨有残留与伪影；优先制作人提供的真分轨 |
| [AccoMontage](https://github.com/zhaojw1998/AccoMontage) | 研究参考，P3/P4 | 乐句选择、结构规划与伴奏纹理 | 重点借鉴选择与结构方法；不等同于任意乐队音频生成 |
| [AccoMontage2](https://github.com/billyblu2000/AccoMontage2) | 首选伴奏试验，P4 | MIDI 旋律→和弦/伴奏，支持段落与纹理控制 | 文档限制含 4/4 和 4/8 小节分段；建立受限用例再试自由结构 |
| [REMAST](https://github.com/CarlWangChina/REMAST-Real-time-Emotion-based-Music-Arrangement-with-Soft-Transition) | 方法与对照，P3/P5 | 前一情绪与目标情绪融合，平滑编曲 | 借鉴过渡方法；确认权重和运行条件，不能假设直接支持局部图编辑 |
| [Music SketchNet](https://github.com/RetroCirce/Music-SketchNet) | 方法参考，P4 | 音高/节奏分离与局部补全 | 原研究针对单声部，不直接覆盖多轨成品音频 |
| [MuseControlLite](https://github.com/fundwotsai2001/MuseControlLite) | 音频生成候选，P4 后 | 时变控制、局部补全及续写 | 用相同片段测控制准确率、耗时、边界；按基础模型要求准备环境 |
| [MusiConGen](https://github.com/YatingMusic/MusiConGen) | 可选对照，P4 后 | 和弦、节奏条件的音频生成 | 不与所有模型同时部署；与 MuseControlLite 二选一做首轮实验 |
| [MIDI-SAG](https://github.com/fundwotsai2001/MIDI-SAG) | 集成参考，长作品阶段 | 旋律 MIDI、和弦与结构化伴奏串联 | 借鉴模块接口和续写组织；不把其能力归为自主创新 |
| [Magenta RealTime](https://github.com/magenta/magenta-realtime)、[MRT2 官方入口](https://magenta.withgoogle.com/magenta-realtime-2) | 后续实时路线 | 文本/音频/MIDI 控制与实时演奏 | 版本和硬件支持不同；Windows 主线不能假设可直接复用 Apple Silicon 运行环境 |
| [FFmpeg](https://ffmpeg.org/)、[Rubber Band](https://breakfastquay.com/rubberband/) | 工程组件，P1/P3 | 解码、导出及变速 | 限制拉伸范围并试听；确认所用构建与许可证 |
| [Pedalboard](https://github.com/spotify/pedalboard) | 可选 DSP 组件，P3 | EQ、混响等音频处理 | 官方为 GPLv3，分发选型需考虑；基础原型可先用 FFmpeg/SciPy |

研究主线建议：先读 AccoMontage2 的结构/纹理接口和 REMAST 的过渡机制，完成自有积木与修复器，再选择一个生成模型。无需下载全部仓库。

## 6. 成熟应用：借鉴什么、怎样对接

| 应用 | 借鉴对象 | 计划接入方式 | 优先级 |
|---|---|---|---|
| [REAPER](https://www.reaper.fm/) | 分轨、Regions、渲染和脚本工作流 | MIDI＋同起点 Stems 导入；后续脚本导入标记 | 首个实际兼容验证对象 |
| [Ableton Live](https://www.ableton.com/en/live/) | Clips、场景及可重复演奏结构 | 第一版文件交换，后续评估同步 | 第二批 |
| [Nodal](https://nodalmusic.com/) | 节点、连接和演奏中编辑 | 借鉴交互及 MIDI 工作方式，不作为 AI 模型 | 设计参考 |
| [Wwise](https://www.audiokinetic.com/en/public-library/2024.1.8_8893/?id=creating_interactive_music&source=Help) | Segments、状态、连接矩阵、过门 | 导出预渲染变奏与 Cue 计划；后续适配自动导入 | 游戏阶段 |
| [FMOD Studio](https://www.fmod.com/studio) | 参数驱动的互动音频工作流 | 将情绪维度映射为运行参数，播放预生成层 | 与 Wwise 二选一验证 |

这些应用已经解决了大量编辑与运行时问题。EmoBlocks 应专注于约束下的内容生成和局部修改，利用成熟编辑器完成精修与播放。插件只是后续交付形态，不单独作为创新贡献。

## 7. 推荐架构与环境

前端 React/TypeScript＋React Flow＋WaveSurfer，简单 SVG 实现可拖动情绪曲线；后端 FastAPI/Pydantic；SQLite 保存项目与版本，文件系统保存不可变素材；MIDI 采用 mido/pretty_midi；分析和渲染由独立工作进程执行，SSE 上报进度。重任务不要阻塞 API 主进程。

模型置于独立环境/服务，通过统一的“约束与上下文输入→候选文件与元数据输出”接口接入。旧研究代码不能假设兼容同一个 Python/PyTorch 环境。阶段 P0 记录操作系统、GPU/内存、推理耗时和来源提交版本，再决定是否使用云推理。

```text
情绪曲线 / 积木编辑
    → 结构化修改请求
    → 约束检查与影响范围
    → 候选生成或复用
    → 局部编排与连接修复
    → 增量渲染与验证
    → 试听 / 接受 / 撤销
    → MIDI、Stems、时间与连接计划
```

自然语言不是核心依赖；规则候选不是最终技术上限。通过统一接口逐步替换候选来源，可独立衡量生成模型对质量的贡献。

## 8. 创新性验证设计

### 数据和对照

先准备 3 组素材测试工程，再扩展到 10～20 段原创或授权旋律，覆盖至少三种曲风。每段设置增强紧张、降低密度、延长时间三类修改。记录模型失败样本，不只选最好听的演示。

- 基线 A：制作人在 DAW 中手工修改分层素材与转场，记录时间。
- 基线 B：分段独立生成＋固定 Crossfade，使用同等素材和尽可能相同的模型。
- 基线 C：EmoBlocks 保持其他部分相同，关闭连接修复或局部更新，分别做消融。
- 完整方案：约束检查＋局部修改＋两侧连接修复。

研究模型无法复现时不编造对比结果；记录阻碍并只比较已运行的基线。手工方案作为质量与效率参照，不预设 AI 会更好听。

### 指标与初始验收目标

| 指标 | 测量方式 | 计划门槛 |
|---|---|---|
| 精确锁定 | MIDI 按锁定字段比较；音频源或冻结区间比对 | 硬约束通过率 100%，失败不自动提交 |
| 修改范围 | 比较修改前后块资产及分轨内容，排除已声明尾音区 | 非影响范围内容不变；顺延只改变位置 |
| 主题辨识度 | 音程/节奏相似度辅助，独立听众识别主题 | 与基线对比，不凭单一 Embedding 宣称成功 |
| 情绪符合度 | 独立估计器与盲听评分，结合目标曲线 | 不使用同一生成打分器自证；报告不同曲风差异 |
| 连接质量 | 盲听自然度，辅以乐句、响度、峰值检查 | 无削波/意外空白；主观结果公开记录 |
| 时长精度 | 输出采样长度、锚点位置和小节约束 | 固定时长模式目标误差≤50 ms；不可行时明确报告 |
| 创作效率 | 从修改请求至满意版本的时间与修正次数 | 先取得基线，再提出改善目标 |
| DAW 可编辑性 | 在 REAPER 导入 MIDI/Stems/时间信息 | 起点对齐、轨道可独立修改、速度映射正确 |

建议 10～15 名参与者完成探索性盲听，音乐经验分层、播放顺序随机、条件响度匹配。小样本只支持原型方向判断，不作普遍有效性结论。保存原始评分、失败率、耗时分布与置信区间。

## 9. 阶段决策与风险处理

- 锁定和影响范围未通过：暂停模型扩展，先修正状态与时基。
- 模型生成不稳定：保留原旋律轨，仅生成伴奏或使用预制候选，继续验证工作流。
- 结构识别误差高：允许手工标段，歌曲自动拆分不阻塞核心演示。
- 情绪曲线有效但转场难听：扩大有限的连接修复窗口；明确延迟和影响范围的取舍。
- 长作品主题漂移：回到显式主题轨与乐句规划，分块渲染，不能把短样本成功外推为八分钟能力。
- 音频生成没有可编辑分轨：只承诺音频层交付，MIDI 输出沿符号编排路径完成。
- 精确时长与乐句完整性冲突：展示选项，由用户决定改时长、调速度或改过门。
